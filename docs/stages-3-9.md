# ТЗ v9.1: этапы 3–9 — план и принятые решения

Рабочий документ для доведения проекта до конца. Решения ниже согласованы с владельцем и **важнее текста ТЗ**, если они расходятся. Непринципиальные мелочи решаются здравым смыслом.

## Что уже сделано (не переделывать)

- **Стек.** Один процесс: FastAPI + aiogram 3 (long polling) + планировщик asyncio (`backend/app`). SQLite через stdlib `sqlite3` (WAL, `BEGIN IMMEDIATE`). Миграции — список `MIGRATIONS` в `db.py`, версия в `PRAGMA user_version`; таблицы с CHECK пересобираются через `_run_script`. Фронтенд — Next.js 15 (static export) + shadcn + Tailwind v4 в `frontend/`. Базу данных не менять — остаётся SQLite.
- **Дизайн «Выход».** Монохромный ink `#161A33`, цвета только для статусов, «линия дня» 8–24. Три колонки начиная с 1024px. iPhone во весь экран, iPad, компьютер. Анимации.
- **Этап 1.** Четыре роли: owner = `ADMIN_IDS`, admin, trainer, employee. Права — в `app/permissions.py` (`CAN`, `can()`, `manages()`). Пауза и блок; мягкое удаление; архивная группа (`Notifier.archive` с хештегами, `/archive_here`, `/archive_off`, таблица `archive_log`); повтор отправки в Telegram.
- **Этап 2.** `app/reports.py`: отчёт = факт + скриншот (`file_id` в Telegram).
  - Отчёт с фактом ≥ плана принимается автоматически.
  - Проверка: принять / вернуть на исправление / отклонить со штрафом.
  - Дедлайн — max(00:00, конец смены + 2 ч).
  - Есть неявки, ручной результат, напоминания и вечерняя сводка; всё настраивается в «Настройках».
  - Штрафы за отчёты пока лежат в колонках `shifts.shortfall_*`.
- **Заготовка этапа 3.** Миграция 7 `_day_actuals`: таблицы `day_actuals`, `day_actual_log`, статус отчёта `approved_team`. Ключи `global_actual_*` в `app_settings.py`. Логика ещё не написана.

## Принятые решения

1. **Общий факт дня (этап 3).**
   - Вводят только владельцы (capability `global_actual`). Ввести и исправить можно в любое время.
   - Каждое изменение пишется в журнал: старое и новое значение, план, кто, когда.
   - В админке — бейдж с числом дней без общего факта.
   - Владельцам уходят пуши: вечером — за сегодня, утром — за вчера. Время настраивается.
   - Общий план дня = сумма объёмов состоявшихся смен.
2. **Пересчёт (этап 3).** Выполняется одной транзакцией при сохранении общего факта.
   - **Команда выполнила план:**
     - Все отчёты дня в `pending_review` (факт < плана) становятся `approved_team`.
     - Сотруднику уходит пуш «✅ Ваш отчет принят автоматически. Общая цель команды выполнена!».
     - В архив — «🟢 АВТОМАТИЧЕСКОЕ ОДОБРЕНИЕ…».
     - Если штраф за недобор уже выдан, предложить аннулировать его с причиной «Команда справилась»: кнопка на всех сразу и на каждого.
     - Отчёт, сданный уже после ввода факта, в такой день сразу принимается как `approved_team`.
   - **Команда не выполнила план:** отчёты с недобором остаются на ручной проверке.
3. **Запрет штрафов за недобор (этап 3).**
   - Штраф за недобор запрещён, пока не введён общий факт дня. Запрет действует в API, в боте и в интерфейсе, с понятной причиной.
   - Если команда выполнила план, такой штраф тоже запрещён.
   - Штрафы за неявку и за поддельный скриншот (факт ≥ плана) разрешены всегда.
4. **Финансы (этап 4).**
   - Таблица `financial_transactions`:
     - тип: `fine` / `bonus` / `deduction` / `payout_offset`;
     - сумма, причина, медиа (`file_id`);
     - статус: `active` / `pending_admin_approval` / `paid` / `cancelled` / `offset`;
     - кто и когда создал и решил, связь со сменой.
   - Все существующие штрафы (окончательная отмена, отчёты, неявки) перенести в эту таблицу. Она становится источником правды для журнала штрафов, статистики и Excel.
   - Окончательная отмена смены создаёт **черновик** штрафа, который ждёт суммы.
   - Штраф от тренера уходит владельцу на одобрение (`pending_admin_approval`). Баланс не меняется до решения.
   - Ещё в этапе:
     - бонусы, баланс сотрудника, аннулирование с причиной;
     - «погасить всё» (только владелец);
     - отчёт `/finances` в боте;
     - быстрые действия в карточке сотрудника: штраф, бонус, аннулировать.
   - Всё, что касается денег, уходит в архив с хештегами `#штраф`, `#бонус`, `#аннулирование`.
5. **Сети (этап 5).**
   - Создавать, менять и закрывать сети может только владелец. На сеть — один тренер, сотрудники привязываются к сети.
   - Тренер видит и делает всё только в своей сети: смены, отчёты, паузы, рассылки по сети, заявки на штрафы.
   - Уведомления по сети приходят её тренеру.
6. **СБП и выплаты (этап 6).**
   - Профиль сотрудника: банк и телефон для СБП. Видят сам сотрудник и владельцы; в списках номер маскируется.
   - Вычеты — только владелец.
   - Мастер выплаты:
     - период и люди;
     - ставки из настроек: базовая ставка и «налог на лень» (порог и ставка). Они переезжают в `app_settings` вместо `pricing.py`, в мастере их можно переопределить;
     - база считается по **одобренному** факту, по дням;
     - тренерам — комиссия с объёма сети;
     - зачёт штрафов, бонусов и вычетов.
   - Реестр с группировкой по банкам, выгрузка в Excel, отметка «выплачено» с фото-подтверждением; запись в архив с `#выплата`.
7. **Рассылки (этап 7).**
   - Существующие переключатели аудиторий (работают / не работают / админы) остаются.
   - Добавить аудитории «по сети» и «выбранные люди», а также фото в рассылке.
   - Подтверждение прочтения: кнопка «Прочитал» в сообщении, список непрочитавших, повторное напоминание им.
8. **Цели (этап 8).**
   - Цели личные, командные и сетевые. Прогресс считается по одобренным отчётам.
   - Цели создаются в админке. У сотрудника — прогресс-бар.
   - Уведомление о выполнении цели.
9. **Живые события (этап 9).** По ТЗ, модуль 7:
   - заявка участника — число и скриншот (`pending_review`);
   - отклонение с причиной и номером попытки;
   - подтверждение победителя (👑);
   - лимит победителей: когда он набран, событие переходит в `finished`;
   - режим накопления (live scoreboard).
10. **Архивная группа.** Только события про деньги, статусы и дисциплину. Всегда с хештегами и тегом человека.

## Правила работы

- **Порядок.** Этапы 3 → 9 строго по порядку. Каждый закрывается целиком: код, тесты, сборка, проверка в браузере, коммит и пуш. Перед этапом перечитать ТЗ по его модулю (текст ТЗ — в первом сообщении сессии или у владельца).
- **Права.** Проверяются через `permissions.py` в API, в боте и в интерфейсе (`CapsContext` / `useCan`). У тренера всё ограничено его сетью.
- **Мутации.** Каждая идемпотентна (`idempotency_key` через `event_logs`) и логируется. Ничего не удалять физически — только менять статус.
- **Бэкенд.** Тесты — pytest в `backend/tests`; запуск из `backend/`: `../.venv/bin/python -m pytest -q`. Вся новая бизнес-логика покрывается тестами, включая права и миграцию со старой версии базы.
- **Фронтенд.**
  - Без ошибок проходят `npx tsc --noEmit`, `npm run lint`, `npm run build`.
  - Скриншоты ключевых экранов — через Playwright: глобальный `playwright`, `executablePath` `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`, Telegram WebApp заглушкой через route на `https://telegram.org/**`.
  - Размеры 390×844 и 1440×920, светлая и тёмная тема. Скриншоты просмотреть и исправить вёрстку.
- **README.** Обновлять разделы про новые функции.
- **Git.**
  - После каждого этапа — коммит и `git push -u origin claude/schedule-bot-miniapp`.
  - Сообщение коммита на английском и заканчивается строками:
    ```
    Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
    Claude-Session: https://claude.ai/code/session_014mJgFSfFnVgoUHqYZD3NAA
    ```
  - Никаких названий и идентификаторов моделей в коде, коммитах и README. PR не создавать.
- **Секреты.** Токен бота и данные сервера никуда не коммитить: они только в `.env` на сервере, а он в `.gitignore`.
