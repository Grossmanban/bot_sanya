# ⚠️ Регламент документации — ОБЯЗАТЕЛЕН для каждого агента

**Обновлено:** 2026-11-17 · **Источник правил:** `AGENTS.md` (корень репозитория)

> [!fatal] Устаревшая или отсутствующая документация — ФАТАЛЬНАЯ ОШИБКА
> Документация в `docs/obsidian/` — единственный источник истины о функциональности для агентов.
> Если она расходится с кодом — агент, который сделал изменение и не обновил доку, допустил
> фатальную ошибку. Расхождение НЕ исправляется «на глаз»: сначала читается код, потом правится страница.

## Правило 1 — ДО работы: читать

Перед любой задачей (новая фича, багфикс, рефакторинг, вопрос заказчика):

1. Прочитать [[README]] (карта документации) и страницы, релевантные задаче.
2. Найти по таблице карты страницу домена, с которым работаешь, и страницу затрагиваемых технических справочников ([[18 - API справочник|API]], [[02 - База данных и миграции|БД]], [[19 - Telegram-бот|бот]], [[20 - Фронтенд Mini App|фронтенд]]).
3. Сверить ключевые факты с кодом (имя функции/эндпоинта/таблицы). Дока описывает «как устроено»; если код явно расходится — доке не верить, сообщить заказчику и исправить доку по коду.
4. «Перед новой системой — найти существующую и доработать её» (правило AGENTS.md): не плодить параллельные механизмы.

## Правило 2 — ПОСЛЕ работы: обновлять

После каждого изменения, попавшего в коммит, агент обязан в **том же коммите** обновить:

1. **Страницу домена** — новое/изменённое поведение, правила, статусы.
2. **Затронутые справочники** — новые эндпоинты, таблицы/колонки, команды бота, экраны, настройки.
3. **Счётчик миграций** в [[02 - База данных и миграции]] — если добавлена миграция.
4. Поле **«Обновлено»** вверху каждой тронутой страницы (дата) и, при крупном изменении, строку в «Истории изменений» страницы.
5. Корневой `README.md` — если изменилось видимое пользователю поведение (README — пользовательская дока).

> [!tip] Признак правильно закрытой задачи
> Другой агент, прочитав только дока-страницы, должен понять новую логику БЕЗ чтения кода.

## Правило 3 — Объём и формат

- Русский язык, стиль существующих страниц. Ссылки на исходники — относительные пути от корня репозитория (`backend/app/alice.py`).
- Каждая страница начинается с блока: `**Обновлено:** ДД.ММ.ГГГГ · **Исходники:** файл(ы)`.
- Таблицы — для перечислений (статусы, ключи настроек, эндпоинты). Колонка «Источник» — файл:строка не нужна, достаточно файла.
- Не дублировать целыми кусками README: дока описывает устройство и правила; README — пользовательские сценарии. Ссылаться словами «см. README, раздел …».
- Новая страница добавляется в карту ([[README]]) в подходящую таблицу.

## Правило 4 — Проверка актуальности (ченжлист ревью)

Перед коммитом чек-лист:

- [ ] Прочитал нужные страницы ДО кода
- [ ] Обновил страницы доменов, которых касается изменение
- [ ] Обновил технические справочники (API / БД / бот / фронтенд / настройки)
- [ ] Проставил новую дату «Обновлено»
- [ ] Если менялась схема БД — добавил миграцию в конец `MIGRATIONS` (см. [[02 - База данных и миграции]]) и обновил счётчик
- [ ] Если менялось видимое поведение — обновил корневой `README.md`
- [ ] Новые тесты — новые страницы не нужны, но [[23 - Тесты и проверки]] обновляется при смене порядка запуска

## Ответственность

| Ситуация | Действие |
|---|---|
| Дока противоречит коду | Код — истина. Исправить доку в том же ПР, сообщить в описании коммита |
| Страницы про новую фичу нет | Создать по образцу существующих, добавить в карту |
| Изменение затрагивает два домена | Обновить обе страницы + справочники |
| Не уверен, где описано | Искать по карте [[README]] и grep'ом по `docs/obsidian/` |
| Доку обновить забыл | Вернуться, обновить, признать нарушение регламента |
