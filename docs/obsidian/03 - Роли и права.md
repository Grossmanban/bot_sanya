# Роли и права

**Обновлено:** 2026-11-24 · **Исходники:** `backend/app/permissions.py`, `backend/app/pending.py`, `backend/app/services.py` (`set_grants`), `backend/app/assign.py` (`may_assign`)

## Роли

Единственное место правил — `permissions.py`. Владелец определяется по `ADMIN_IDS` из `.env` (не по полю БД).

| Роль | Кто это | Сфера |
|---|---|---|
| `owner` (Владелец) | Telegram ID в `ADMIN_IDS`, может быть несколько | Всё, включая деньги, блокировки, роли, сети, факт дня |
| `admin` (Администратор) | назначает владелец (`users.role='admin'`) | Все сотрудники: смены, отчёты, штрафы сразу, паузы, рассылки, настройки. Без денег/блокировок/ролей |
| `trainer` (Тренер) | назначает владелец; ведёт одну сеть (`networks.trainer_id`) | Только своя сеть (включая людей инструкторов). Штрафы — на согласование |
| `instructor` (Инструктор) | назначает владелец | Только закреплённые (`users.instructor_id`). Смены, отчёты, паузы; штрафы — на согласование |
| `employee` (Сотрудник) | после одобрения | Свой график, отчёты, баланс |

Ключевые функции: `role_of()` (owner>role из БД), `is_staff()` (есть панель), `sees_everyone()` (owner+admin),
`manages(actor, target)` — инструктор: своим по `instructor_id`; тренер: своей сети по `led_network_id` (сеть, где он trainer_id).

## Матрица возможностей `CAN`

`can(actor, capability, target)`: роль в списке + (если указан target) `manages(actor, target)`. В Mini App список
приходит в `GET /api/me` → `capabilities` (фронт скрывает разделы, сервер всё равно проверяет).

| Capability | Роли | Что открывает |
|---|---|---|
| `money` | owner | вычеты, выплаты, погашение штрафов, реквизиты чужие |
| `block` | owner | блокировка/разблокировка |
| `roles` | owner | назначение ролей |
| `global_actual` | owner | общий факт дня (`/fakt`) |
| `networks` | owner | управление сетями |
| `invites` | owner | приглашения владельца, «Обновить все ссылки» |
| `fine_direct` | owner, admin | штраф сразу (тренер/инструктор — только заявкой) |
| `approve_fines` | owner, admin | решение по штрафам тренеров |
| `forgive_fines` | owner, admin, trainer, instructor | «Простить» штраф (тренер — своей сети) |
| `fine_request` | trainer, instructor | штраф на согласование |
| `bonus` | owner, admin, trainer | бонусы своим |
| `pause` | owner, admin, trainer, instructor | пауза |
| `work_status` | owner, admin, trainer, instructor | «Работаю/Не работаю» подчинённого (18.11: сам сотрудник тумблер не трогает) |
| `review` | все персонал | проверка отчётов/неявок |
| `schedule` | все персонал | правка чужих смен |
| `broadcast_all` | owner, admin | рассылка всем |
| `broadcast_network` | все персонал | рассылка своим (инструктор — своим людям) |
| `settings`, `points` | owner, admin | настройки, справочник точек |
| `registrations` | owner, admin | заявки, онбординг, запросы обучения |
| `grants` | owner, admin | личные разрешения в «Команде» (18.11) |
| `profiles` | owner, admin | изменение профилей сотрудников |
| `remind_profiles` | все персонал | «Напомнить о заполнении» |
| `manuals` | owner, admin | методички (создание/выдача) |
| `export` | все персонал | Excel-отчёты |
| `raspred` | все персонал | распред (тренер — своей сети) |
| `assign_points` | owner, admin, trainer, instructor | 24.11: раздел «Смены → Распределение по точкам» и «Отправить график». Само право на каждого человека проверяет `assign.may_assign` (см. ниже), т.к. грант расширяет сферу не через `manages()`: владелец/админ — любой сотрудник; тренер — сотрудники своей сети (без других руководителей); инструктор — только свои люди. Личный грант `assign_points` — любой сотрудник из любой сети. Руководители (кроме владельца и админа, которые и так всё могут) цели не являются; заблокированные — тоже |

| `access_log` | owner, admin | «Попытки доступа» |
| `groups` | owner, admin | группы «Предзакреп»/«Основная» |
| `products` | owner, admin | выдача доступа к продуктам «Работы» |
| `alice` | owner, admin | QR, запросы, модерация, статистика «Алисы»/«Плюса» |

## Личные разрешения (гранты, 18.11)

Поверх ролевой матрицы — три пер-сотрудникских тумблера в «Команде» (карточка человека → «Личные разрешения»).
Колонки `users.can_broadcast_all`, `users.can_onboard` (18.11) и `users.can_assign_points` (24.11), меняют владелец/админ
(`POST /api/admin/team/{id}/grants`, сервис `svc.set_grants`, событие `GRANTS_CHANGED`). Карта `GRANTS` в `permissions.py`:

| Флаг | Расширяет | Эффект |
|---|---|---|
| `can_broadcast_all` | `broadcast_all`, `broadcast_network` | сотрудник/инструктор пишет всей команде, тренер — и вне своей сети; список людей и сетей в «Рассылке» — все; подпись всё равно по реальной роли («от сотрудника» и т.п.) |
| `can_onboard` | `registrations` | заявки, анкеты, обучение и приём в команду — без подтверждения админа; карточки новых заявок и запросов обучения в боте тоже приходят ему (`svc.onboarding_telegram_ids`) |
| `can_assign_points` | `assign_points` | 24.11: «Распределение по всем точкам» — держатель (любая роль, включая сотрудника) распределяет **любого** сотрудника на любую точку вне своей сети и подчинённости, открывает раздел «Распределение» и пишет график своим людям; тексты «Распределения» (шаблоны вида `assign`) ему доступны, шаблоны рассылок — нет |

Правила: `has_grant()` проверяет флаг; `is_staff()` пропускает держателя любого гранта в панель (обычному сотруднику
открывается вкладка «Админ» с его разделами); `manages()` при этом никого не добавляет — гранты не дают «видеть всех»
в «Команде»/отчётах (кроме `can_assign_points`, чья сфера — отдельная функция `assign.may_assign`). Заблокированный/пауза — как обычно, гасят всё.

## Состояния аккаунта (влияют на доступ)

- `status`: `pending` (заявка/анкета) → `approved` / `rejected`. Отклонённый молчит.
- `account_state`: `active` / `paused` (пауза с причиной: запись закрыта) / `blocked` (бот и приложение закрыты полностью — `block_guard` в боте, 403 в API; человек исключается из рабочих групп). **19.11: заблокированного можно «Скрыть из списка»** (кнопка в карточке «Команды», право `block`, `users.hidden_at/hidden_by` — миграция 52): скрытый уходит из «Команды» и всех списков выбора (`/admin/users`), остаётся только в свёрнутом блоке «Скрытые» с кнопкой «Вернуть»; разблокировка возвращает в списки сама — «активный и скрытый» состояния не бывает. Мастер выплат заблокированных и так не показывает — скрытые из него исчезают тем более.
- `work_status`: `working` / `not_working` — «Не работаю» закрывает запись смен, новые выполнения «Алисы», заявки в события; напоминания не идут. Сколько дней в статусе — `work_status_at`, `status_days`. **18.11: тумблер переключают только начальники** — инструктор своим людям, тренер своей сети (включая инструктора), админ/владелец любому (`manages(actor, target)`, `svc.set_work_status`); сам сотрудник переключить не может, персонал — свой статус может.

## «Ждут решения» (pending.py)

`GET /api/admin/pending` и команда бота `/pending` — одни и те же счётчики `pending.counts(conn, viewer)`.
Правило «один запрос — один ключ»: просмотр ничего не сбрасывает, только решение; человек с нарушением за день
считается в «Дисциплине», а не в «Дне»; pending-человек с анкетой — «Онбординг».

Ключи: `review`, `no_show`, `violations`, `urgent`, `unmarked` (сегодня+завтра), `events_pending`, `fines_pending`,
`fines_draft`, `registrations`, `onboarding_new`, `internship_review`, `training_requests`, `profile_changes`,
`payment_changes`, `actual_missing`, `actual_overdue`, `alice_moderation/failed`, `plus_moderation/failed`.
Область видимости — `scope()`: owner/admin все, тренер/инструктор только свои.

19.11: `internship_review` считает только идущую стажировку (цель набрана или тренер попросил завершения) —
завершённая стажировка с непроверенным вторым этапом нигде не «висит решением»; плитка «Онбординга» в приложении
считает только `onboarding_new` (фронт, `TILE_COUNTS`), ключи остаются в «Решениях» и `/pending`.
